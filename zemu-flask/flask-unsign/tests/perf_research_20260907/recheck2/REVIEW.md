# 最新源码复审（2026-09-07）

结论：WordSet 迁移和缓存基本功能通过验证，前次混合搜索漏查修复仍有效。发现两个新增性能/内存问题；前次的 OpenCL 跨队列提交和补验统计问题仍未解决。本轮只新增审核材料，没有修改生产代码。

源码复制到本目录 `src/` 后独立编译；编译使用 GCC 16.1.0、`-O3 -std=c++26 -Wall -municode -static -static-libgcc -static-libstdc++`，链接 zlib。编译无报错或警告。测试结束后逐文件 SHA-256 与工作区生产源码比较，没有变化，见 `source_provenance.json`。

## 发现

### [P1，遗留] OpenCL 事件生产队列没有提交保证

位置：`src/gpu/ocl.cpp:555`、`:585`、`:597`。

`prefetch()` 将拷贝放入 `q2`，随后 `q` 的 kernel 等待该事件；主线程调用 `clFinish(q)`。这些新拷贝入队后，没有 `clFlush(q2)` 或针对生产队列的隐式 flush 操作。初始化阶段的 `clFinish(q2)` 在这些拷贝之前，退出阶段的调用又在 `clFinish(q)` 返回之后，均不能保证此处生产者向设备提交。

这是跨驱动正确性问题：允许延迟提交的实现可能一直等待；本机 OpenCL 实测没有卡死，不能因此推断所有实现正确。普通内存缓存命中的一次性上传路径不经过该流水，因此缓存命中测试也不能覆盖首次 pinned 上传的这个风险。

修复建议：解析 `clFlush`，将它接入复制队列提交点，并检查返回值；保留计算和上传重叠，不以每块 `clFinish(q2)` 替代异步提交。[Khronos 官方规范](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clFlush.html) 明确要求跨队列消费事件前提交事件所属队列。

### [P2，新增] 缓存预算按逻辑大小计算，严重低估持有容量

位置：`src/flask.cpp:666`、`:708`；关联 `src/crack_cpu.cpp:169`。

加载器先按整个文件大小分配 `bytes`，压缩后仅 `resize(w)`，并不释放多余容量；`off.reserve(n/24+16)` 也可能留下大量空闲容量。但缓存准入、打包回填预算和日志均使用 `size()`。因此设置的内存预算不能约束缓存持有的缓冲容量。

确定性复现：文件内容为 10 MiB 换行加 `key\n`，环境变量 `ZK_DICTCACHE_MB=1`，调用实际 `loadWordSet` 和 `dictCacheStore`，输出：

```text
budget=1048576 admitted=1 accounted=11 capacity_bytes=12233452 words=1
```

这不是工作集采样误差：探针直接读取实际 vector 的容量。预算 1 MiB，却接纳了至少 11.67 MiB 的缓冲区容量，记账仅 11 字节。探针见 `cache_probe.cpp`，结果见 `cache_capacity.log`。

修复建议：用所有容器的 `capacity()*sizeof(value_type)` 计算准入和回填预算；如果主动收缩，再按收缩后的实际容量判断。将预算解释为缓存持有内存，与任务临时内存峰值分开统计。

### [P2，新增] 单次 CLI 也复制整份 GPU 打包缓存，付出无法复用的开销

位置：`src/flask.cpp:891` 附近的缓存获取，以及 `:1061` 至 `:1068` 的回填。

`flaskCrackImpl` 不区分单次 CLI 和常驻模式；默认预算允许时，首次 GPU 请求会将 `idxMapL`、`skippedIdxL` 和 pinned 打包内容复制到全局缓存。单次 CLI 随后退出，副本不会被复用，原始缓冲又仍需供当前请求使用。1600 万个 8 字节候选的本轮夹具因此额外复制并持有约 256 MB（索引 128 MB，打包字节 128 MB，不含 allocator 开销）。

本机交错 A/B：当前版本、GPU、16 线程、相同未命中字典，禁用缓存的总耗时中位数 2.856 s，默认缓存 2.970 s，增加约 4.0%。这只是当前设备状态下三轮数据；收益幅度不可外推。但单次请求创建不可复用副本的逻辑成本是确定的。

修复建议：由调用方传入是否需要跨命令缓存，只在 serve/interactive 中启用打包副本，或采用有明确复用触发条件的缓存策略。

### [P2，遗留] 补验工作仍漏计时间，且循环不响应取消

位置：`src/flask.cpp:1128`、`:1164`，计时终点在 `:1095`、`:1148`。

混合和纯 GPU 分支都先固定 `secs`，随后才顺序标量验证 `skippedIdx`。包含大量超长或 NUL 候选时，补验可能成为主要开销，最终显示的耗时仍排除它；尝试次数也未按这段实际工作更新。补验循环内部没有读取 `g_crackAbort`，因此进入补验后取消不会立即停止后续候选。

修复建议：把补验纳入总计时及尝试计数；按固定批次检查取消。是否并行/SIMD 化应另用长词分布基准决定。本轮确认代码路径，未进行操作系统取消信号专项复现。

## 本轮端到端性能观测

使用既有 `tests/wl-bench16.txt`，160,000,000 字节、1600 万词，未命中全扫，16 线程。每项先预热一次，再进行三轮交错测量，每轮反转执行顺序；计时包含进程启动、加载、搜索及退出。旧版是前次审核保留的 `recheck/zemu-flask.exe`，并非任意 git 基线。

| 配置 | 总耗时中位数 |
|---|---:|
| 前次审核版本 CPU | 1.276 s |
| 当前源码 CPU，默认缓存 | 0.571 s |
| 当前源码 GPU，禁用字典缓存 | 2.856 s |
| 当前源码 GPU，默认字典缓存 | 2.970 s |

该工作负载的 CPU 总耗时下降约 55.3%，说明这轮包含 WordSet 的修改有实际收益。这不是独立 loader 阶段测量，不能等同于注释所写的加载速度提升比例。本轮没有同步记录 GPU 频率、功耗或其他负载，不能据这组 GPU 数据推断所有设备/规模的引擎排序，也未测量 serve 缓存复用的性能收益。

原始轮次、标准错误输出和二进制哈希见 `benchmark_results.json`；复现脚本为 `bench_review.py`。

另一个兼容性变化：当前加载器明确拒绝大于 `UINT32_MAX` 字节的文件，以前逐行表示没有这一固定文件大小限制。如果必须继续支持大字典，应选择分片或宽偏移；本轮没有创建大于 4 GiB 的测试文件。
