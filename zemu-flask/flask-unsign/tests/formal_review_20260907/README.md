# 混合字典调度与 WordSet 的局部形式化验证

这次使用 Z3 5.1.0，不是增加随机测试或多跑几轮。`verify.py` 把从当前源码提取的性质写成 SMT 公式，求解“前提成立且性质不成立”是否存在解。每个证明义务还单独检查前提可满足，避免矛盾前提导致空洞通过。

结果：18 个义务中，16 个返回 **UNSAT**；另 2 个故意撤销修复的检查返回 **SAT** 并给出反例。UNSAT 的含义是该公式在明确的模型与前提下没有反例，不代表未经建模的整个程序正确。[Z3 官方说明](https://microsoft.github.io/z3guide/docs/theories/Bitvectors/) 展示了通过否定性质并检查不可满足性进行证明的方法。

## 调度模型和归纳不变量

选择任意候选 `x`，满足 `0 <= x < N`，对字典设置 `0 < N <= UINT32_MAX`。这个范围来自当前加载器限制，属于保守上界。这里没有穷举到某个小 N，也没有限制调度迭代次数。

- `H`：GPU 承诺处理的原始字典前缀终点。
- `T`：CPU 已领取后缀的起点。
- `R`：GPU 已完成前缀终点，是证明用的辅助状态。
- `cs`：该候选的 CPU 状态，分别为未领取、待处理、已验证、已丢弃。

归纳不变量为：

```text
0 <= R <= H <= N
0 <= T <= N
cs == 未领取  <=>  x < T
cs == 已丢弃  =>   x < H
```

求解器验证初始状态成立，并验证 CPU 领取、CPU 丢弃、CPU 验证、GPU 领取、GPU 完成这五种抽象状态转移均保持不变量。失败 CAS 和其他不改变这些状态的操作属于停顿转移。

对陈旧读取，模型允许 CPU 读到任意 `0 <= seenH <= H`；GPU 允许读到任意 `T <= seenT <= N`。这覆盖了单调 head/tail 的数值陈旧读取，并不要求读到最新值；同一 GPU 生产者读取自己最后发布的 head。

然后验证正常耗尽时调度前沿已经相遇，即 `H >= T`。当已承诺的 GPU 工作完成、CPU 没有待处理候选、被 GPU 跳过的候选已补验时，任意 `x` 必满足以下至少一项：

```text
CPU 已验证 x
或 x 可由 GPU 表示，且 x < R
或 x 不可由 GPU 表示，且已完成补验
```

由于 `x` 任意，得到该抽象模型内的全空间覆盖性质。这里证明的是覆盖安全性；没有证明线程公平调度、无饥饿或 GPU 必定完成。

数学整数与 C++ 无符号数不能直接混同。因此另用 **64 位位向量**验证了当前字典范围内 GPU 加法/钳制保持严格推进和边界合法，也验证了 CPU 饱和减法不会下溢。大规模掩码的全部可达数值范围未纳入这次结论。

## 两个反例校验

1. **恢复旧版 head 过量发布。** 求解器自动找到 `N=65537, x=1`。CPU 先领取 `[1,65537)`；GPU 实际只承诺 `[0,1)`，却发布 `head=16777216`；CPU 据此丢弃候选 1，GPU 又不处理它，产生漏查。当前发布实际终点的实现排除了这一原因。
2. **撤销 skippedIdx 补验。** 使用可达状态：CPU 领取 `[1,65537)`，GPU 领取 `[0,1)`；候选 0 为不可打包词，其他候选中存在可打包词。删除补验后候选 0 没有任何验证者。这里刻意避开“整个字典都不可打包时直接全 CPU 回退”的另一分支。

这些是对旧缺陷/撤销修复的模型反例，不是声称当前版本重新出现了这两个缺陷。

## WordSet 局部证明

设原始文件长度为 `n`，当前行起点为 `i`，行终点为 `eol`，去掉尾部 CR 后的长度为 `length`，压缩写游标为 `w`。在：

```text
0 <= w <= i <= eol <= n <= UINT32_MAX
0 <= length <= eol-i
```

下，求解器证明 `w+length <= eol <= n`，因此本行 `memmove` 不覆盖分隔符后尚未读取的后续行；写游标仍可由 u32 表示，继续到下一行时保持写游标不超过读游标。

这只是算术和区间安全证明，不包含文件读取成功、每个词的完整解析等价性、分配器行为或整个 WordSet API 的内存安全证明。

## 尚未证明的部分

- 模型是按实际代码手工抽象；没有通过自动 C++ 前端、CBMC 或编译验证建立全程序对应关系。
- 陈旧读取使用数值抽象；没有用 C++ 弱内存模型工具独立验证该抽象涵盖全部语言级执行。
- 假设成功完成的 backend 确实验证了所承诺区间里的每个可打包候选。`rawMap`/`lower_bound` 的实现对应、SIMD/HMAC/OpenCL kernel 的计算正确性没有证明。
- 假设正常未命中结束，无取消、线程异常、分配失败或中途 GPU 错误；错误恢复应建立独立状态转移与后置条件。
- 仍未证明 OpenCL 活性。前次发现的跨队列缺少 `clFlush` 不能被这里的覆盖安全性证明消除。
- Z3 输出的证明对象已保存，但未由独立证明检查器再次验算；求解器本身属于信任基础。
- 性能速度和实际设备行为仍需测量，形式化验证不能替代性能基准。

如果下一步需要直接对 C/C++ 实现做有界内存安全检查，可为解析、打包和错误恢复建立 CBMC harness，并保留 unwinding assertions；否则循环展开不足可能漏掉行为。这是后续路线，本次**没有运行 CBMC**。[CBMC 官方说明](https://www.cprover.org/cprover-manual/cbmc/unwinding/) 解释了展开边界及其断言的必要性。
